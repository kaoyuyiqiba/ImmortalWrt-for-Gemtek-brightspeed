# XR1710G 10G 网口与原厂量产固件对照

日期：2026-11-11。核对代码：本地 `xr1710g-stock-hardware-alignment` 分支，检查起点 `9e5ae76a6a5b582baaa9977a8cdd6f634d332f4e`（B17 加上一轮硬件补齐）。本轮没有连接路由器、刷机或修改运行配置；结果属于离线源码和二进制核对，不是 10G 吞吐验收。本轮未重新确认 GitHub 最新 HEAD，上游信息以已取得的本地补丁为准。

## 1. 结论及本次修改

两个 10G 电口是外置 Realtek RTL8261 PHY，连接路径是 Airoha MAC → PCS/SerDes → USXGMII → RTL8261 → 网线，不是 PCIe 网卡。当前主链路 PCIe Gen3 x2 的配置直接服务无线，不能将两者的训练问题混为一谈。USXGMII 的内部串行速率与网线协商的 1G/2.5G/5G/10G 速率也不能直接画等号。

核心引脚映射、MDIO 地址、收发极性与量产证据相符；没有发现足以据此将 PHY 全套初始化改回原厂的依据。本轮发现并补齐一处确定的板级配置遗漏：

- 文件：`target/linux/airoha/dts/an7581-gemtek-xr1710g-ubi.dts`。
- 地址 8 的 10G WAN PHY 已有 GPIO31 和前后各 200ms 复位等待，但缺少 `reset-before-id-read`；现补上。
- 同文件地址 5 的 10G LAN PHY，以及 `an7581-xr1710g.dts` 中两个 PHY 原本已有该属性。
- 当前内核 `drivers/net/mdio/fwnode_mdio.c:fwnode_mdiobus_reset_phy_before_id_read()` 只有读到该属性才执行预先 GPIO 复位，再读取 PHY ID。因此遗漏时可能在复位解除/SMI 就绪前识别 PHY；是否在本机造成故障仍需冷启动测试。
- **如果使用的是 `an7581-xr1710g` 构型，这次一行修改不改变其行为。不能把此补齐称为已解决当前运行固件的 WAN 或 Wi-Fi 故障。**

本次保留所有现有 PHY 微码、EEE 策略和 PCS 校准/恢复补丁。对证据尚不足的寄存器没有猜测性写入。

## 2. 原厂参考及定位方法

主要参考为量产 XR1710G 5.1.1.12：[固定提交内的原厂镜像](https://github.com/akorshun/xr1710g-backup-and-flash/blob/1da28af0821a53e64e36c19381c178ae9d5ce39d/firmware/xr1710g-stock-5.1.1.12-tclinux.bin)。工程机备份仅为此前辅助参考，本轮没有烧录工程文件。

- 原厂容器 SHA256：`4b3a3191007bb197061445cf605a6fd528100ab5c5b6b25d53b9d900408cc83f`。
- 解压内核 SHA256：`4b74cbb519a6eedf229b43c9c8bb7fbca2c56a1620cf9a8fdedbe364345f291e`。
- 原厂 `rtk-ms-phy.ko` SHA256：`4de464940e1a88ee7cadd66d8702a6413c20fc23669f39da8721cac6dfd98f1f`。
- 当前 RTL 固件构建源：`rtl826x-firmware-2026.01.24~0cd4abe2`，实际内核为 Linux 6.18.60。

`stock-rtk-ms-phy.asm` 是模块的 `objdump -dr`，保留重定位。模块地址应按“节名 + 偏移”引用；例如 `.text.unlikely+0`，不是内核 Image 的文件地址。不能把待重定位的 `bl` 占位值当成真实调用。

原厂内核已恢复 kallsyms，`_stext - 0x800` 为映像基址。本报告的 `stock-eth-*.asm` 和 `stock-kernel-*.asm` 地址是解压内核文件偏移，区别于模块地址。原厂包含多个同名 USXGMII 实现；通过 `ETH_XSGMII_DRV_init` 的 platform_driver 指针确认 ETH probe 为文件 `0x22fd4`，对应 ETH 函数族约 `0x19070–0x22fd4`。没有把 PCIe 辅助 SerDes 的同名函数当成 ETH 的实际调用。

已有参考补丁：

- 743：恢复 `realtek,patch-rtk-serdes` 板级可选调优；引用 [OpenWrt 46d81ac](https://github.com/openwrt/openwrt/commit/46d81ac28caf2e0018089da921e9ae953f6dd3d2)。本轮网络获取该提交超时，依据为本地已有补丁，不声称在线核验其最新状态。
- 628：SDK `linux/arch/arm64/mach-econet/sgmii/air_eth_xsgmii.c:RX_PRCal()` 的 crossing search。
- 745：W1700K E2 冷启动 RX 校准问题，并将对应路径覆盖到 XR1710G 使用的 PON PCS。
- 629/630：USXGMII 速率适配先于发布链路、CDR 重试退避。
- 744/747：铜侧协商后 flow_s 重调，以及 phylink in-band 配置后的 PCS 复位/重调。

这些补丁均已存在于检查起点，本轮没有将其重复计为新增修复。完整标题、引用和说明保存在 `现有补丁参考与说明.txt`。

## 3. 板级连接与复位核对

| 项目 | 原厂证据 | 当前代码与结论 |
| --- | --- | --- |
| 两颗外置 PHY | Clause45，地址 5、8；模块 `rtk-ms-phy.ko` | 同为地址 5、8；不能误套另一条 `rtl8261x_*` C/D 型号路径 |
| 10G LAN | 原厂第二 GPIO bank 的14；SDK probe 使用对应 GPIO mux 选择 | 统一编号 GPIO46；`gdm4 → phy5 → lan2` |
| 10G WAN | 原厂第一 GPIO bank 的31；地址8 probe 选择该 GPIO mux | GPIO31；`gdm2 → phy8 → wan` |
| 复位电平/等待 | GPIO mux 证据确认管脚，不能仅凭 `SET_GPIO*_EN` 名称推断完整脉冲 | active-low，assert/deassert 各200ms，保留；UBI WAN 补上预读ID复位 |
| PHY 收发极性 | 原厂 `.text.unlikely+0x138–0x14c`：MMD30 `0xc1` 掩码及值均 `0xc0` | 两个 DTS 均 tx/rx invert；当前驱动写同一组极性位，一致 |
| 协商 | 原厂通用 C45 铜侧协商 + host SerDes | 当前 USXGMII + `managed="in-band-status"`，按带内状态协商，不强制网线10G |
| 低功耗 | 原厂提供独立低功耗函数，未证明最终运行策略与当前相同 | PMA suspend 默认禁用；100M/1G/2.5G/5G/10G 的 EEE 默认禁用以保稳定 |

原厂 `.text+0x190` probe 的 GPIO 调用可确认复用管脚选择，但本轮未完整复原量产 bootloader 到 Linux 的全部外部复位波形。因此，本次 `reset-before-id-read` 是基于当前内核明确语义和同板另一构型的一致性补齐，不称作复制原厂复位时序。

## 4. PHY 初始化及恢复的实际差异

### 内部复位与补丁顺序

原厂 `.text.unlikely+0x40–0xdc` 可还原为：先等待约50ms；MMD30 `0x145 bit0` 置1后清0；再等约30ms；调用 `phy_patch`。随后配置中断和极性。

当前 `rtl826x_config_init()`：先禁止 PHY 中断输出；`0x145 bit0` 置1；等待30ms再清0；解除失败最多尝试6次；等待150ms再加载固件，最后设置极性。两者都在内部复位后加载微码，但脉冲长度、就绪等待、中断处理不同。当前等待更长本身不能认定为缺陷，本次保留。

原厂随后还写 MMD30 `0x19=0x0154`、`0x1a=0x020c`、`0x1b=1`、`0x1c=0x020c`。本轮没有可靠公开寄存器说明来证明其完整用途，**没有把它们当作 SerDes 校准项照搬**。原厂读取 SDS `7.0x10` 和 `6.0x12` 用于打印；这些读取不是向它们写入调优值的证据。

### flow_s 与 PCS 复位

当前可选补丁在通用微码末尾追加 SDS `7.0x10=0x80aa`、`6.0x12=0x5078`。铜侧协商或重开接口后，还执行 `7.0x10=0x8003 → 等10–12ms → 0x80aa`，再写 `6.0x12=0x5078`。这是本地已有 743/744 补丁记录的 SDK/实测调优；本轮没有在原厂 `config_init` 的直接写操作中独立证明上述最终值，不能将已有补丁的结论冒称为本轮新逆向证实。

需要优先关注的差异是 747：`rtl826x_config_inband()` 向 MMD3 `CTRL1` 写 RESET|SPEED10G，随后直接执行 flow_s；未显式轮询 RESET 自清。已有 743 的说明记录：DTE XS 复位曾清掉 SDS `6.0x0d`、`6.0x0e`、`6.0x1d` 的固件配置，导致 PHY 侧锁定却没有 MAC 侧带内字。

**这构成值得实机核查的候选冲突，但不是已证实的本次故障根因。** 747 的 PCS 复位是否等效、是否清同样的位，必须比较复位前后读数；只重写两个 flow_s 寄存器未必能覆盖全部变化。本轮没有贸然删掉 PCS 复位，也没有在缺少时序依据时加任意延迟。

### 掉链恢复

当前 PHY flow_s 状态机在铜侧 AN 完成后尝试；恢复 carrier 即停止；未恢复则经过120次状态轮询宽限后重试，没有总次数上限。120次是轮询次数，不应始终解释为精确120秒。

当前 SoC PCS 在 link down 且 SigDet 仍有信号时，先给未完成 AN 的状态3次轮询宽限，再进行 CDR reset，并按1/2/4/8秒间隔退避。board opt-in 时普通 PHY SDS reset work 被跳过，避免它与 flow_s 同时复位。

原厂也有 RX 校准、CDR reset、AN restart 和中断处理，并不是“从不恢复”。本轮提取了 ETH `RX_PR_CAL_SEQ`（文件0x1cc90）、`AN_ReStart`（0x1ec70）、`xsgmii_interrupt`（0x1e3e4）。尚未证明当前全部 retry 条件、全部模拟写序列与原厂逐条等价，因此不凭静态代码断言两层恢复已互相干扰。

## 5. RTL8261 微码表精确比较

原厂 ELF 表项为20字节；前10字节为操作数，后面含 compare/SRAM 元数据。当前固件为10字节 packed 操作。比对时统一操作枚举，按相同操作序列对齐，避免因插入一条导致后续全部假差异。

以下为 `rtl8261n_c_*` 命名表，数字为操作数；“共同操作”是序列匹配数，不等于执行次数或覆盖率。

| 表 | 原厂 | 当前 | 共同操作 | 结论 |
| --- | ---: | ---: | ---: | --- |
| NCTL0 | 51 | 51 | 51 | 操作数一致 |
| SDS | 103 | 103 | 103 | 操作数一致，比较元数据未等同 |
| UC | 10 | 10 | 10 | 操作数一致 |
| normal | 21 | 21 | 20 | `PHYOCP 0xa438` 最后一项原厂7、当前5 |
| top | 17 | 17 | 15 | TOP page0x5a/reg0x12、0x13：原厂7、当前5 |
| NCTL2 | 878 | 858 | 854 | 有代码/表项差异 |
| algxg | 78 | 32 | 29 | 有差异 |
| alg_giga | 5 | 2 | 2 | 有差异 |
| RTCT | 176 | 0 | 0 | 当前此表为空，不据此认定10G功能缺失 |
| AFE | 2 | 0 | 0 | 当前此表为空 |
| dataram | 148 | 84 | 84 | 当前序列可在原厂中对齐，但并非同一张完整表 |
| UC2 | 282 | 240 | 135 | 有明显差异 |

当前生成器逐项输出源码表前10字节，未使用 compare/SRAM 元数据；本轮没有模拟原厂 SDK 完整执行环境，所以本表不能当作两套实际 MDIO 执行轨迹完全比较。差异细节见 `rtl8261-aligned-table-comparison.json`。本轮深度表比对限于命名的 RTL8261N 表，不声称同时逐项核对了全部 RTL8264B 表。

**软件包日期2026.01.24不能证明所含微码比原厂更新。** 当前 `conf_rtl8261n_c.c` 的注释日期为2022-11-15；原厂与当前的7/5差异，在没有可靠版本说明时也不能单凭数值判断谁更适合本机。此前“保留更新固件”的表述应限定为保留当前仓库软件包，不应作为微码年代结论。

在隔离目录重新编译实际固件生成器，三份 `.bin` 与构建目录现有文件逐字节一致。RTL8261N 常规版共1437条操作，14370字节，SHA256 `ae1963b2a84a17eaa2fb9052591bdb5152838feda045d7313f45a8608b918533`。LP版是另一份镜像，源码注明功耗更低但最大线长降到50m；本轮没有切换LP版。实际选择N/8264B由 VERSION_ID variant 位决定，本轮没有读取实体机该位来重新确认。

## 6. SoC PCS 与速率适配

当前 USXGMII 的速率适配支持10G、5G、2.5G、1G、100M，分别更新 PCS mode 和 rate adapter。629补丁在解析到新的带内速率后、发布链路前先写适配器；link_up 仍会再写一次，缓存用于避免每次轮询都写寄存器。没有发现把10G固定限制为1G的 DTS 设置。

原厂 ETH `USXGMII_10G`（文件0x1bd70）也会同时配置 PCS 与 rate adapter：可见适配器 `+0x00` 使能以及 `+0x2c bit8` 的处理。当前走 Linux phylink 回调和速率缓存，不能将原厂单次初始化函数与整个运行状态机作简单一对一比较。本轮没有对所有速率组合和硬件 revision 完成逐写等价证明。

原厂与当前对外部PHY和内部交换机端口的命名、网络拓扑抽象也不同。不能照抄原厂 `eth0` 的 VLAN 文本作为当前 DSA/MAC 配置。

## 7. 本轮验证结果

- 两套 DTS 修改前后均编译成功；既有 dtc 警告分别12条/11条，按警告类型、节点、内容比较无新增。没有执行完整 dt-schema 验证。
- 从最终 DTB 反编译，确认两种布局的 PHY5/PHY8 均具有预读ID复位属性和200000µs的assert/deassert等待。
- 正向补丁以零fuzz应用成功，反向补丁恢复原文；`git diff --check` 通过。
- 实际固件生成器重新编译、执行成功；N、N_LP、8264B三份二进制均复现现有结果，1437/2308/2170条操作的位域范围合法。
- 本轮未重建整机固件，也未做10G对端吞吐、冷启动或拔插验收。没有因此声称10G稳定性或Wi-Fi问题已解决。

## 8. 后续实机验收方法

先保留可恢复固件，通过有线管理口抓日志；每次只改变一个变量。建议同时采样 `wan`、`lan2` 的 `ethtool`、`ethtool -S`、`ip -s link` 和 `logread`，记录MDIO地址、PHY驱动、AN/PCS carrier、CRC/FCS错误、丢包、重置和恢复次数。日志限额轮转，避免写满存储。

1. 分别做冷启动和软重启各至少10次，检查两颗PHY都被识别，尤其UBI WAN；记录首个PHY ID可读和carrier出现时间。不能只看最后能否ping通。
2. 用支持对应速率的可靠对端，依次测试1G/2.5G/5G/10G，记录双方协商、线材、MTU、EEE和错误计数；拔插和速率切换至少20次。千兆电脑无法验收10G吞吐。
3. 在独立有线服务器上运行 `iperf3 -s`；客户端分别执行 `iperf3 -c <服务器IP> -P 4 -t 600`、加 `-R`，再加 `--bidir` 做双向，保存JSON并分别报告每方向Mbps、重传和断链。客户端与服务器至少具备目标速率，服务器CPU也需足够。
4. 先测LAN二层转发，再分别测WAN路由/NAT/PPPoE；确认流表命中后再评价PPE/NPU吞吐。路由器本地iperf会终结在CPU，不能代表硬件转发上限。
5. 对747复位候选问题，用受控MDIO调试记录 MMD3 CTRL1复位位，SDS `6.0x0d/0x0e/0x1d`、`7.0x10`、`6.0x12` 及MAC侧AN_STATS。对比复位前、复位完成后、flow_s后；避免并发操作SDS间接地址窗口。只有出现“复位后特定位丢失、恢复这些位后稳定”的可重复证据，才新增针对性修补。
6. 同步保留无线MT7996消息超时和PCIe AER时间线。10G铜侧掉链、USXGMII失锁和无线PCIe CmpltTO应分别定位；本轮发现的10G配置差异不能直接解释此前三频Wi-Fi全部消失。

## 9. 应用与回退

补丁以检查起点 `9e5ae76a6a5b582baaa9977a8cdd6f634d332f4e` 为基准。它不是相对于任意时刻GitHub“最新版本”的保证；其它版本先运行 `git apply --check`。只修改UBI DTS一行，可用同目录正反向补丁应用或回退；重新生成固件后才会影响实体机。

本地隔离分支提交包含中文说明；主构建树本轮未修改。报告附带参考哈希、原厂反汇编、微码表差异JSON、DTB编译记录及固件复现结果。未将工程mtd、个体EEPROM、账号密码或整个原厂二进制打包为刷机材料。
