# XR1710G B19 异常修复与合并合理性检查

日期：2026-11-12。基线：B19 `9e9c04583030a8747e2d325b96e28ee406218a73`；候选分支 `xr1710g-B20`。本轮先修复已证实的用户态问题，不将所有日志警告归因为无线硬件故障。

## 1. 已确认并修复：DAWN 信标报告触发空指针崩溃

仅回移4个上游修复，保留当前2026-06-10源码pin和现有6GHz补丁，不整包跳版本；作者、提交链接保留在内层补丁头。DAWN包release由1升2。

## 2. 已修正配置：PPPoE的WAN6绑定

实际WAN为PPPoE，三层设备 `pppoe-wan`，而wan6原绑定物理以太网 `wan`。依据当前OpenWrt netifd逻辑接口语义，改为 `@wan`。本机仅重启wan6，未重拨PPP；状态确认其设备变为 `pppoe-wan`。完整配置备份留在路由器 `/root/xr1710g-B20-runtime-backup/network.before-wan6`，不上传含拨号凭据的配置。

镜像迁移脚本仅匹配gemtek,xr1710g、wan.proto=pppoe、wan6.proto=dhcpv6，且wan6原设备等于WAN底层物理口时才修改。DHCP上网、自选其他IPv6设备、其他机型不受影响；重复执行不再改变配置。

当前PPP链路没有IPv6链路本地地址/默认路由，改完绑定后wan6仍为pending。因此仅能宣布绑定错误修复，不能宣布IPv6已恢复。未关闭odhcpd告警、未强制通告不存在的默认路由，未为获取IPv6擅自重拨PPP。

## 3. hostapd netlink丢包：有界缓解候选

本机libnl-tiny中 `NLE_NOMEM=5`，ENOBUFS与ENOMEM均映射至此；因此 `nl_recvmsgs failed: -5` 不是可直接解释为Unix EIO。实机 `/proc/net/netlink` 的inode3000累计Drops=3449，映射到hostapd PID2204 fd23。当前MemAvailable约1.6GiB，不能把该日志直接当作整机内存耗尽；历史每次-5的底层errno没有逐次记录，不能断言全部由同一路径触发。

现有上游 `nl80211_register_eloop_read` 已说明阻塞事件循环会导致netlink突发积压，并将所有接收缓冲设为256KiB。本机rmem_max=1MiB。本地候选将仅信标事件socket的请求额度提高至1MiB，其他控制/管理socket保持256KiB，仍受内核rmem_max限制，失败时保持既有回退行为。每个wiphy最多增加有限缓冲额度，不设置无限队列，不隐藏报错。

这是依据实机丢包的本地缓解，非来自量产固件的原样移植，也不是mt76或PCIe故障根治。hostapd包release从6升7；仅做源码与编译验收，尚未替换实机wpad或验证丢包改善幅度。

## 4. 2.4GHz低速仍未定位

B19整夜双向四流约上传134.59/下载3.21Mbps。本次补测每段30秒：

|模式|上传Mbps|下载Mbps|
|---|---:|---:|
|单向，每方向4流|156.39|182.25|
|双向，每方向1流|121.70|41.65|
|双向，每方向4流|148.49|5.80|

可见单向下行并没有固定卡在3Mbps，问题随双向多流竞争加重。尚不能区分终端竞争、TCP确认/调度、无线队列和NPU路径，不将此结果宣布为驱动根因或已修复。镜像额外补充仅在保留配置缺少2g htmode时写入HE20的迁移脚本；这是B19验收发现的配置缺失修复，明确不是双向不对称的修复。已有htmode不被覆盖。

## 5. 经合理性检查不强行修改

- Watchdog：内核airoha_wdt默认heartbeat=24，32位计数器max_timeout按实际时钟计算；源码说明150MHz时上限28秒。procd请求30失败后GETTIMEOUT回退24，实机ubus确认running/timeout24/frequency5。未扩大硬件可表示上限、未关闭喂狗，未修改通用procd默认值牵连其他平台。该启动警告仍会出现，尚不作为功能故障处理。
- PPE统计：当前源码已包含9999-14/15两张上游兼容补丁。NPU返回-22时继续建立转发，并将统计显示为unsupported/n/a，不因统计不可用退出。没有伪造计数或改用不同NPU固件来消除提示。
- factory nvmem device-link：启动后的PHY/网口已经工作；当前没有因该警告导致网卡失败的证据。未更改校准数据来源或强行移除设备依赖。
- rdinit、未配置fstab、未配置ZeroTier等启动消息：未据此修改分区、关闭正常服务或删除功能。
- DAWN与usteer同时运行：保留为策略冲突风险，未将其当作已证实的段错误原因，也未擅自删除任一组件。
